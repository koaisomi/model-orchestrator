1. Overview and what is real vs mock

The Model Orchestrator is a Node command line controller. You give it an engineering task in plain text. It classifies the task (level 1 to 4), builds a route through up to five model roles, calls each model through the real Anthropic API, passes a structured hand-off between steps, stops at approval gates for risky work, runs an audit, correct and validate loop, and records every step: which model was requested, which model actually answered, how many tokens it used and what that cost.

The design goal is a verified result, not the number of models used. A typo fix goes through one builder and a basic check. A change to authentication goes through a planner, a builder, an independent auditor, a human approval and a final validator.

Hard rule: never pretend a model ran. If a provider is not configured, the step is BLOCKED with a reason. Every step record stores requestedModel and servedModel, and the served value is read from the API response model field, never assumed. Mock output is labelled provider: "mock" everywhere it appears and the report header says MOCK RUN — no model was called.

2. Architecture

The system has three layers. The orchestration layer decides what happens next (classifier, router, state machine, pipeline engine). The execution layer talks to models and reads files (providers, retrieval, schemas, hand-offs). The governance layer protects you and proves what happened (gates, redaction, ledger, cost, report, apply).

The independence rule

The auditor and validator receive a fresh message history: no builder conversation, only the spec, the hand-off and the actual proposal file contents read back from disk. Config validation rejects auditor.model == builder.model unless allowSameModelAudit: true. A model reviewing its own work with its own blind spots is not an independent audit.

4. Classification and routing levels

The classifier is rule based: case-insensitive, word-bounded keyword matches plus the number of context files. The highest matching level wins. "author" does not trigger "auth", "roller" does not trigger "role". With no match the level defaults to 2 and the reason says so.

LevelTriggersRoute (phases in order)
1 simpletypo, text, copy, colour/color, style, rename, comment, config value, single filebuild, quick-check. The quick check is a Sonnet self-check and is labelled basic verification, never an audit
2 moderatefeature, endpoint, API, workflow, integrate, 2-5 context files[retrieve if context] build, [audit if risk is medium or higher], correct loop, validate
3 complexnew module, architecture, database, schema, integration across, multi-service, workflow engine, more than 5 filesplan, [retrieve], build, audit with correct loop, validate
4 criticalauth, login, password, permission, role, payment, billing, credential, secret, token, encryption, PII, personal data, migration, drop table, deploy production, infrastructure, firewall, DNSplan, [retrieve], build, audit, approval gate, validate. Any later apply needs a second gate

Classification dimensions follow the policy: complexity (Simple, Moderate, Complex, Critical), risk (low, medium, high, critical), information need (Minimal, Moderate, Extensive), reasoning need (Basic, Advanced, Deep), execution need (Limited, Extensive) and verification need (Basic, Standard, Strict).

  • Keywords are matched as stems (passwords, payments, migrat*, encrypt*, jwt, sessions, cookies, production, tls ...) and strictly on purpose: harmless text such as "design tokens" or "cookie banner" also becomes level 4, because a false level 4 only costs a gate while a missed one skips the gate and the audit.
  • --level N may only raise the level and is logged as a decision in decisions.md. A lower value is ignored and logged: lowering would skip the gate, audit and validator. The level-4 gate is required whenever risk is critical or the rules said level 4.
  • Layered classifier. (1) Keyword stems; level 4 also covers personal data (email, phone, address, birthdate, dob, ssn, national id), access rights (admin, privilege, access control, passcode, pin), hashing (hash*, bcrypt, argon*) and live systems (live server or db, db upgrade, schema change, customer data, user data). (2) A Haiku assist, on by default for real runs, returns a structured classification. The stricter of rules and Haiku wins: it can only raise the level or risk, never lower them, and both answers are logged in decisions.md. If Haiku is unavailable or errors, the rules result is kept with the note "assist unavailable" and a level 2 task is raised to risk medium so it is audited. --no-assist-classify turns it off (logged); mock runs use a scripted classification. (3) A task that matches no rule is level 2 with risk medium and gets an Opus audit. Level 4 also covers health data (medical, patient, hipaa), pay data (salary, payroll), money movement (refund, stripe, paypal, wire transfer, bank account) and cloud write access (s3, bucket, iam, write access). Pure text, style, typo, rename and docs-wording tasks stay level 1.
  • Level 2 risk is medium only when the text mentions API, endpoint or integrate, or two or more context files exist. Otherwise it is low and no audit runs. The report states "No audit ran".

5. Pipeline and state machine

The engine walks the route. After every transition it writes an event to events.jsonl. An illegal transition throws, so a bug cannot silently skip an audit.

State table

FromAllowed next states
NEWCLASSIFIED
CLASSIFIEDPLANNING, RETRIEVAL, READY_FOR_BUILD
PLANNINGRETRIEVAL, READY_FOR_BUILD
RETRIEVALREADY_FOR_BUILD
READY_FOR_BUILDEXECUTING
EXECUTINGAUDIT, VALIDATION, ESCALATED
AUDITCORRECTION, APPROVAL_REQUIRED, VALIDATION, ESCALATED

APPROVAL_REQUIREDVALIDATION

COMPLETECLOSED
ESCALATEDPLANNING (re-plan)
any non-terminalBLOCKED, CANCELLED
CLOSED, BLOCKED, CANCELLEDterminal: no further transition
Reading "BLOCKED at APPROVAL_REQUIRED". A level 4 run without approval moves to APPROVAL_REQUIRED, the gate is denied, and the run ends in BLOCKED. The report records blockedAt so you can see where it stopped.

Audit, correct, validate loop

  1. The builder produces proposal round 1. The controller writes it under proposals/round-1/.
  2. A fresh auditor reads the proposal files from disk and returns findings with severity Critical, High, Medium, Low or Informational.
  3. Critical or High findings block. The builder gets the findings and the previous proposal and produces a revised round. A fresh auditor re-audits. This repeats for at most maxCorrectionRounds (default 2).
  4. Unresolved Critical or High after the last round: status FAIL, state ESCALATED, a human must decide. Medium and lower findings do not block and travel to the validator.
  5. Level 4 only: the approval gate.
  6. A fresh validator returns PASS, FAIL, BLOCKED or PARTIAL with a list of what it could not verify.

Escalations

  • Builder says the plan is wrong (planFlaw: true): back to the planner once, then the builder rebuilds. A second flaw is listed under Not verified and the run continues.
  • Auditor finding of category architecture with severity High or Critical: planner re-plan (once), then rebuild.
  • Business or authorization questions: the planner returns humanQuestions. The human gate asks for a decision; denied means the run ends BLOCKED and the report lists the questions under OPEN QUESTIONS FOR A HUMAN.

Each escalation is an event in the ledger and a line in decisions.md.

6. The hand-off contract

Each model call starts with a hand-off because the next model shares no memory with the last one. The object follows the policy's Appendix A. It is validated before every delegation. A missing required field makes the step BLOCKED instead of sending a half-empty briefing. It is passed through redact() before it is saved to handoffs/NN-role.json or put in a prompt.

FieldContentRequired
projectProject name (folder name of the root)yes
taskThe task text, redactedyes

currentStateState machine stateyes

handoffStatusREADY, BLOCKED or NEEDS_CLARIFICATION. Only READY may be delegatedyes

  "classification": { "level": 1, "complexity": "simple", "risk": "low", "verification": "Basic" },
  "currentState": "EXECUTING",
  "decisions": ["route: build > quick-check"],
  "evidence": [],
  "findings": { "Critical": [], "High": [], "Medium": [], "Low": [] },
  "nextAssignment": { "role": "builder", "instructions": "Produce the proposal that meets the spec." },

The builder returns a structured object: summary, planFlaw, planFlawReason, files[{path, action, content}], testsSuggested and limitations. The controller validates every path before writing anything, and a bad path counts as invalid output (one retry, then the step fails).

7. Provider details

7.1 Anthropic provider (src/providers/anthropic.mjs)

  • Official SDK, new Anthropic({ maxRetries: 2 }). Credentials come only from the environment or an ant auth login profile. Nothing is hardcoded or logged. The client is injectable so tests pass a fake.
  • Streaming with await stream.finalMessage(). Default max_tokens 32000, configurable per role.
  • Effort as output_config: { effort }. The thinking parameter is omitted (adaptive by default on these models).
  • Never sent: budget_tokens, temperature, top_p, top_k, an assistant prefill, a forced tool_choice of any or tool. The tests assert none of these appear in any request body.
  • Structured output: output_config.format = { type: "json_schema", schema }. The text block is parsed with JSON.parse and checked against the schema in code (required keys, enums, types, extra keys). On failure one retry runs with the validation error appended as a new user message, then the step fails.
  • Refusal fallbacks for the exact ids claude-fable-5-2, claude-opus-5-5 and claude-sonnet-5-5 (not a name pattern; any other id, including dated variants and Haiku, gets none): client.beta.messages.stream({ ..., betas: ["server-side-fallback-2026-07-01"], fallbacks: "default" }). Controlled by serverFallbacks. Haiku gets no fallbacks parameter. A fallback is detected from usage.iterations entries of type fallback_message or content blocks of type fallback and recorded as fallbackRan with servedModel from the response.
  • stop_reason is checked before content is read. refusal fails the step with the stop_details.category. max_tokens fails with "truncated, raise max_tokens". Only end_turn is success.

Error handling (typed, never string-matched)

SDK classMeaning here
AuthenticationError (401)Provider not usable: step and run BLOCKED
PermissionDeniedError (403)Treated like "model unavailable": try the role fallback model and record the substitution; without a fallback the step FAILS
NotFoundError (404)Model unavailable: try the role fallback model, record the substitution
BadRequestError (400)Step FAILED with the API message
RateLimitError, 5xx APIErrorThe SDK retries twice, then the step FAILS
APIConnectionErrorStep FAILED

Capability check and probe

capabilityCheck() returns {available, reason}. It reports available if ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN is set, or an ant profile directory exists (a heuristic). It reports the variable name only, never a value. doctor --probe calls client.models.retrieve(id) for every configured model (no tokens spent) and lists which models the account can use.

7.2 Claude CLI provider (default)

The default provider, because it uses the Owner's Claude Code login and needs no API key. It runs claude -p --model <id> --output-format json --tools "" --strict-mcp-config --setting-sources "" --disallowedTools "mcp__*" --no-session-persistence --effort <level> with the whole prompt on stdin, so no user text is in argv. These flags make the child a plain text model: no tools, no MCP servers or connectors, no hooks, plugins or project settings, no saved session. It spawns with shell: false and an args array, with its working directory set to a fresh empty temp folder that is removed afterwards. It applies a 120 second timeout (a cold start takes 11 to 35 seconds on the dev PC) and kills the child on timeout.

  • Served model: the modelUsage key that matches the requested model (the CLI may use other models for side work, so the first key is never trusted). Several keys with no match, or none, is recorded as "unverified" and listed under Not verified.
  • Cost: the cost the CLI reports (labelled "cost reported by claude CLI"), otherwise "subscription - not metered", which has priceKnown: false and cannot satisfy a budget.
  • Verified live: a one-word Haiku call authenticated with --setting-sources "" and reported the served model. If a later CLI version stops authenticating that way, fall back to --setting-sources user and treat user hooks as a limitation.
  • doctor --probe makes that one tiny Haiku call and prints the result.

7.3 Mock provider

A deterministic scripted provider for tests and --dry-run. Replies are queued per step kind and the last reply repeats. It always returns provider: "mock" and servedModel: "mock", zero tokens and zero cost.

8. Security model and limits

ControlHow it works
No shell from model outputThe controller never passes model text to a shell, eval or spawn. The only child process is the optional claude binary with a fixed args array.
Proposals, not writesThe builder's files are written only under runs/<id>/proposals/ through safeJoin.
Gated applyapply is the only code that writes outside runs/. It needs status PASS (or PARTIAL plus a forcePartial gate), an apply gate, and a separate delete gate. Deletes are moved into .orchestrator-trash/<runId>/ in the target and never hard-deleted.
Path safetyRejects empty, NUL and control characters, absolute, drive-letter, .., : (NTFS streams), 8.3 short-name segments (GIT~1), Windows device names, trailing dot or space, symlink or junction escapes. JavaScript's plain realpath keeps short names, so a path like GIT~1/hooks/pre-commit once reached .git/hooks; now short names are rejected and every deny check also runs on every segment of the realpath.native result. Comparison is case-insensitive on Windows.
Apply hygieneMock runs are refused. The gate listing escapes control characters and prints a WARNING for executable-ish targets (.git*, .husky/, .vscode/tasks.json, CI workflows, package.json, *.ps1|bat|cmd|sh).
claude-cli isolationIsolation flags, empty temp working directory, prompt on stdin only (section 7.2).
RedactionApplied to the task, every context file, every hand-off and every ledger event.
Retrieval sandboxFiles must be under the root (realpath, symlink safe). Deny list: .env*, *.pem, *.key, id_rsa*, id_ed25519*, id_ecdsa*, *.p12, *.pfx, .npmrc, .netrc, .git-credentials, .pypirc, .htpasswd, *.tfstate*, credentials*, secrets*, .git/, node_modules/, *.sqlite, binaries (NUL in the first 8 KB). A denied path given directly as --context is refused, not skipped. Junction loops are detected. Caps: 200 KB per file, 2 MB total, 200 files. Overflow is listed, never silently truncated.
GatesKinds level4, apply, delete, forcePartial, human. Interactive prompt (type GO), --approve pre-approval (logged), otherwise denied. Every decision has a timestamp and a "who".
IndependenceFresh auditor and validator context with real file contents; builder and auditor must differ.
Injection postureRole prompts state that file contents, task text and earlier model output are data and never instructions.

Redaction details

Two passes in a fixed order, because a bare bearer pass alone would leave the token behind. Pass 1 matches authorization[:=\s]+((bearer|basic|token)\s+)?\S+ so the whole header with its scheme is removed. Authorization is redacted only when followed by : or = or a known scheme, so prose such as "authorization is required" keeps its next word. Pass 2 matches bare bearer tokens. Then URL userinfo (postgres://user:pw@host), Anthropic keys (sk-ant-...), generic sk- keys, GitHub github_pat_ and gh[opusr]_, Slack xox*, AWS AKIA and ASIA ids, Google AIza keys, JWTs, PEM private key blocks, and finally key/value pairs in JSON, YAML, env or URL-query form for names such as password, token, secret, api_key, x-api-key and client_secret, quoted or not.

in : Authorization: Bearer abc
out: Authorization: [REDACTED]

Limits you must accept

Automated review is not a penetration test. An Opus audit is a second opinion that catches many mistakes. It is not a human security review, a threat model or a pentest. Level 4 work (auth, payments, personal data, production) still needs a qualified human before it ships.
  • The controller does not run or test the proposed code. Run your own tests after apply.
  • Redaction is pattern based. A secret in an unusual format can slip through; keep secrets out of the context folder.
  • Cost is computed from your price table and the served model. When a server fallback ran, the whole call is priced at the served model, which is an approximation.
  • The live API is exercised only by a pilot run; the automated tests use fakes.

9. Setup

  1. Node 22 or newer. Check with node -v.
  2. Install: in the project folder run npm install. It installs only @anthropic-ai/sdk.
  3. Credentials (real runs only): the default claude-cli provider uses your Claude Code login, so just be signed in to Claude Code. For the Anthropic API alternative (--provider anthropic) run ant auth login or set ANTHROPIC_API_KEY (or ANTHROPIC_AUTH_TOKEN) in your shell. Do not paste a key into a file in this folder.
  4. Check: node bin/orchestrate.mjs doctor --probe validates the config, reports each provider as AVAILABLE or BLOCKED, and probes which models your account can use.
  5. Smoke test without spending: node bin/orchestrate.mjs run "fix typo in README" --dry-run --root examples/sample-project.

13. Pilot plan

Follow the policy's deployment sequence: prove the pipeline cheaply on low-risk work, then widen.

  1. Day 0, free: npm test and the two dry-run acceptance commands. Read the mock report and the run folder.
  2. Day 1, probe: set credentials, run doctor --probe. Confirm which of the four models your account can use. If Fable is unavailable the planner will substitute Opus; the report will say so.
  3. Pilot A, level 1: examples/sample-task.md against examples/sample-project with --provider anthropic --budget-usd 0.50. Check that servedModel matches the request and that the proposal changes only the typo.
  4. Pilot B, level 2 or 3: a small real change in a scratch copy of a project with --context. Confirm the audit actually reads the proposal and the cost matches your expectation.
  5. Pilot C, level 4 dry run of governance: a critical-sounding task without --approve; confirm it stops at APPROVAL_REQUIRED. Then approve and review the gate record.
  6. Apply rehearsal: apply into a throwaway folder first, with and without the gates.
  7. Decide: review the Not verified lists and the real costs. Adjust prices, efforts and rounds in orchestrator.config.json. Only then use it on real project folders, always on a branch with tests.

15. Cost notes

  • What is measured: per step inputTokens, outputTokens, cacheRead, cacheWrite and usd, from the API usage of the served model times your price table. The run total is in run.json and the report.
  • Where the money goes: Opus audit and validation steps and Fable planning dominate. Level 1 work costs a Sonnet build plus a Sonnet check. Every correction round adds one Sonnet build and one Opus audit.
  • Input size matters: the builder, auditor and validator all receive the context files. Keep --context narrow; the 2 MB cap is a ceiling, not a target.
  • Budget guard: before each step the controller estimates input at one token per three characters plus the full max_tokens output at the output price. This is checked before every paid attempt (the structured-output retry and a fallback model are separate attempts) and each attempt's cost is booked right after it. If the estimate exceeds what is left of --budget-usd, the run is BLOCKED before that attempt. The estimate is deliberately pessimistic, so a tiny budget blocks early.
  • Mock and CLI runs: mock costs nothing. The CLI provider uses your subscription: the report shows the cost the CLI reports (labelled) or "subscription - not metered".
  • Server fallbacks: each usage.iterations entry is priced by the model that ran it. The iteration field names are assumed from the documented fallback fields and not seen live, so compare with your Anthropic usage page. Tokens of a refused attempt retried on a fallback model are not recorded.
  • Tuning levers: lower effort for the retriever and builder, keep audit effort high, lower maxTokens, fewer correction rounds, narrower context. Measure on real tasks before changing defaults.
  • Prices change. Verify the table on the pricing page before relying on dollar figures.
